# Automatic payment-pause resume

## Why payment apps refuse, and when Detach must already be off

Google Pay India blocks payments when it finds an "unknown or unauthorised" app with an active accessibility service ([Google Pay help](https://support.google.com/pay/india/answer/17165523)). The likely mechanism is Play Integrity's app-access-risk verdict, which reports enabled control-capable accessibility services and excludes only Play-reviewed accessibility tools ([verdicts](https://developer.android.com/google/play/integrity/verdicts)). A sideloaded Detach with `isAccessibilityTool="false"` always counts while its service is enabled. It cannot be hidden: the enabled-services setting and Play services' attestation see every enabled service, and declaring itself an accessibility tool would misrepresent Detach (it is not an assistive tool) and violate Play policy. Other UPI and bank apps vary; some reportedly refuse while *any* accessibility app is on.

Payment apps can check at launch, before their first window exists. Detach can only react to a window event, so a pause triggered by the UPI app itself is inherently late. Community testing also reports that newer Google Pay versions keep the block until the phone restarts once it has seen such a service, so after one failure every retry can fail even when Detach then pauses correctly. Detach therefore aims to be switched off **before** the payment app starts:

1. **Select the apps you pay from.** The selection (`Settings.paymentPackages`) is not limited to UPI and bank apps: an investing, broker or shopping app that launches Google Pay can be selected too. Opening it pauses Detach, so it is already out of `enabled_accessibility_services` when the checkout launches the UPI app, including the common case where a checkout SDK starts the UPI app by explicit package inside its own task.
2. **Pause first, or "Pause and open".** The authenticated "Pause for payments" control is available in Detach, in the status notification and as a **Quick Settings tile** (`PauseTileService`). The tile can only be bound by System UI (`BIND_QUICK_SETTINGS_TILE`) and only opens the same non-exported `PauseActivity` confirmation; it never pauses by itself. On the lock screen it asks Android to unlock first. For opening a UPI or bank app directly (no checkout app involved), `PauseActivity` lists the selected apps that have a launcher entry as **Pause and open <app>**. After the same confirmation it pauses, then polls `Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES` every 50 ms for at most two seconds and starts the app's plain launcher intent (new task, no data or extras) only once `io.github.detach` is no longer listed. If Detach is still listed after two seconds, the app is not opened, so it never runs its check against a Detach that is still on.
3. **Reactive fallback (late, best effort).** Opening a selected app straight from the launcher is detected from its own window, after its process and first activity already exist, so a launch-time check can still see Detach. An accessibility event alone is not evidence that the sender is in front: any app can send events from the background. Detach therefore pauses on a selected app's event only while Android reports no active window at all (the gap while a new app takes focus). Whenever another app is the active window, including the home screen, an unselected checkout app or Detach itself, it only re-checks the active package a few times (about 50 ms to 1 s) and pauses if the selected app's window takes focus. Package names only; no content is read. On the main thread, one active-window read per event is reused rather than repeated.
4. **Order of work when pausing.** The durable pending marker is committed, then the optional monitor start is attempted while the service is still bound (system-bound foreground-service allowance), then overlays are removed and `disableSelf()` is called. Alarm replacement, the paused notification and diagnostics follow after Detach is already off.

If Google Pay still shows "Payments blocked… restart your phone", restart once. Detach stays paused through the restart: the pending pause and its reminder are restored, but boot invalidates automatic authority, so resume by tapping **Resume protection** in Detach. Another enabled accessibility app can cause the same block; Detach lists other enabled non-system accessibility apps by label in its Payments section (read from the component names in `enabled_accessibility_services`; nothing is stored) and links to Accessibility settings. It never switches other apps' services off.

**Not yet verified on a phone:** how quickly `enabled_accessibility_services` drops Detach after `disableSelf()` on every OEM build; whether a UPI app launched inside a checkout's task always delivers an event to Detach (Android 14+ can hide views marked accessibility-data-sensitive from services that are not accessibility tools); and when exactly Google Pay requests its attestation. Selecting the app you pay from does not depend on any of these.

**Rejected: a `upi://pay` relay.** Detach does not register for UPI intents to pause and forward them. Checkout SDKs mostly launch the chosen UPI app by explicit package, so a relay would never be called; a relay would have to receive and forward UPI URIs containing amounts and payee addresses (against Detach's privacy constraints) and return the UPI app's result strings correctly; it would add an exported intent handler; and Detach would appear to the UPI app as the calling package, which may feed its risk checks.

## Modes and permissions

The default payment pause fully disables Detach's accessibility service and schedules one timer for the selected 1–60 minutes. No Usage Access monitor runs by default. The timer cannot know whether the bank is still foreground; it may re-enable protection while the payment app is still open, after which the service pauses again at once if a selected app is the active window (the payment app may notice the moment Detach was on). Choose enough time for the transaction, or resume manually when finished. The one thing the timer can see is whether the phone is in use: while the screen is off or the keyguard is locked, a due timer reschedules itself every 30 seconds instead of resuming, because a payment app left on its PIN or OTP screen checks again when the phone is unlocked, and Instagram/YouTube cannot be used while locked anyway. This wait is bounded: once less than 20 minutes of the pause's automatic authority (duration plus one hour) remain, the timer resumes even if the phone is locked.

Automatic enablement requires the owner's optional `WRITE_SECURE_SETTINGS` grant. Installing Detach does not grant it. Without that grant the pause remains pending and the due notification/app explains the manual Accessibility Settings fallback; an automatic attempt does not authorize a Settings reconnect or claim that protection is running. An explicit Resume action can authorize one manual Settings reconnect for three minutes.

For manual recovery, open Detach, tap **Resume**, then use Android Settings → Accessibility → Downloaded/Installed apps → Detach → enable the service within three minutes. Names vary by manufacturer. Merely opening Accessibility Settings, opening Detach or tapping the ongoing monitor notification does not authorize a reconnect. If a request expires, return to Detach and explicitly tap Resume again.

Owners who want true automatic background resume can grant the optional development permission themselves from an authorized computer:

```sh
adb shell pm grant io.github.detach android.permission.WRITE_SECURE_SETTINGS
```

This is a powerful Android development permission, not a normal runtime permission prompt. Detach uses it only to restore its own accessibility-service entry while preserving other entries. This implementation does not run the command, install anything, or change grants on the owner's device. If a grant is absent/revoked or a secure-settings write fails, use manual recovery rather than assuming protection has resumed.

“Resume when Instagram or YouTube opens” is a separate, default-off consent setting. It additionally requires Usage Access and the secure-settings grant. Enable it from Detach's consent UI, then enable Usage Access for Detach in Android Settings. If the device has no package-specific Usage Access screen, open Settings → Special app access → Usage access and select Detach. No monitor is started merely by opening the app, tapping its notification, rebooting, updating the app, or granting a permission.

## Detection, battery and privacy limits

The optional monitor runs only during a valid pending payment pause. A dedicated `HandlerThread` queries recent Usage Events approximately every **two seconds**, only with an interactive screen, no keyguard lock and unlocked user storage. Queries cover at most the most recent **ten seconds**, never before this pause began; after the first query they normally cover only the time since the last check. A single event buffer is reused. No wake lock, network request, third-party runtime dependency, content/class-name inspection or usage-history persistence is used. The app still requests neither `INTERNET` nor `QUERY_ALL_PACKAGES`.

This is near-immediate **best effort**, not instantaneous detection or a hard real-time upper bound: ordinary detection is within approximately one polling interval **after Android makes the event available**, plus binder/scheduler delay. Usage Events are not a topmost-window or payment-completion API; OEM behavior, delayed/missing events, multi-window and process termination can delay or prevent detection. There are no device measurements proving a battery/RAM improvement or a particular battery cost.

Only package names, foreground/background event types and timestamps are processed. Recent foreground and unresolved selected-app package hints are held in memory, not written as a history. A selected-app hint (UPI, bank or an app you pay from) takes priority over a social hint. A selected app observed moving to the foreground lasts until Android reports that it moved to the background, so sitting on one payment or PIN screen does not look like "finished"; it is bounded by **ten minutes** without a new event. The app that started the pause predates the monitor's query window, so it is pre-filled: held the same way only if the pause came from its own active window (or a startup re-check that read it), and otherwise (a pause from an event alone, or "Pause and open" before the app has started) only as a 30-second hint until a real foreground event arrives. This is safe only because observation must be continuous: screen lock/off or a query gap longer than ten seconds discards all cached state. After an unlock (or monitor start, or a gap), a due timer waits until observation has run for one full poll, so a payment app coming back to the front on unlock is seen before the timer may resume; during those first two polls the timer-side check also counts as "payment known". Social foreground hints still expire after 30 seconds. The timer-side payment hint is additionally accepted only if a query completed in the last four seconds, and each deferral is 30 seconds within the pause's bounded automatic authority (duration plus one hour). Once a hint is gone, foreground is **unknown**, not “banking finished”; the timer may resume, and the service then pauses again at once if a selected app is still the active window (see below). Do not rely on this monitor to establish transaction completion.

The foreground service has a private ongoing notification, an explicit immutable tap into Detach, no binder interface and no exported component. The public lockscreen version has no package information. Both notification versions request `localOnly`, an advisory bridge/companion-device hint, not an absolute guarantee against forwarding by privileged/system notification listeners. Disabling the feature, revoking Usage Access, ending a pause or completing a resume stops it. Screen-off/lock removes polling rather than scheduling repeated checks. An AppOps listener observes Usage Access revocation even while screen-off. Android's foreground-service task manager can also stop it. The service is non-sticky and is never restarted after boot or process death; if killed, the timer/manual fallback remains.

## Authority and fail-closed behavior

Starting a pause must successfully commit its durable pending marker **before** the parent accessibility service disables itself. `Pause.begin(...)` returns false on failure; callers must leave protection running in that case.

Automatic authority is bound to a unique pending pause, the original wall and elapsed start times, duration and boot count. Wall/elapsed ages must agree within five seconds. Timer authority is valid only at/after both original deadlines and for at most one additional hour; it is not renewed by a late delivery, app lifecycle callback, notification tap, boot or update. Boot/update explicitly invalidate it. A stale, malformed or mismatched marker remains paused with manual fallback. An automatic attempt is single-use. A successful secure-settings write retains the pending marker until the accessibility service consumes a separate wall/elapsed/boot-bound, single-use reconnect authorization and reports that it started. The legacy `ACTION_RESUME` broadcast remains ignored.

Rendering reminders must not cancel an authorized due alarm that Android has not delivered yet. App opening/UI countdown refresh may restore the original future alarm but cannot invent a new deadline or automatic token. A fresh known-payment hint at delivery may defer the single outstanding alarm by 30 seconds, preserving timer fallback if the monitor is then killed. This does not change the original pause deadline or extend authority; invalid/stale authority still requires manual fallback.

**No exemption for a selected app in front.** There is no post-resume exemption: if a timer or monitor resume reconnects the service while a selected app is the active window, the startup check pauses again immediately, and because the active window is often unavailable right after binding, the service re-checks the active package at about 50, 150, 300, 600 and 1000 ms. Earlier previews suppressed the original bank for three minutes after a timer resume to avoid a "loop"; that let Detach stay enabled inside the payment app on retry, so it was removed (stale suppression keys are ignored and deleted). No suppression is needed against a tight enable/disable loop: every reconnect needs fresh authority (a timer due at least one pause length after the new pause began, a newly observed Instagram/YouTube foreground, or an explicit Resume tap), and a selected app's foreground never grants it. In timer-only mode a resume over a selected app still re-enables Detach for a moment before it pauses again, which a payment app could notice (Google Pay may then block until a restart); choose enough time or enable app detection. Only app detection keeps the timer waiting while a selected app is in front, and the app's Payments copy says so only in that mode. No package learned from Usage Events is persisted by the monitor.

## Android 12–15 foreground-service constraints

The monitor is a narrowly declared `specialUse` foreground service with `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_SPECIAL_USE`, plus its manifest subtype explanation. It does not impersonate a media, location, health or data-sync service. Android 14 requires the declared type/permission. `specialUse` has no runtime prerequisites of its own, but does not bypass ordinary startup restrictions, and distribution through Google Play may require review of this use case.

On Android 12+, background FGS starts need a platform exemption; a visible user action is supported, and the background-start documentation also refers to apps permitted to start activities from the background. A system-bound accessibility service can qualify under the documented system-bound-service allowance, but a later disabled service or generic background callback must not be assumed to qualify. Detach attempts startup only as part of beginning the pause, before accessibility is disabled, catches denial and falls back to timer/manual behavior. Acceptance of a start request is not proof that the monitor is running. Android 15's visible-overlay requirement for the `SYSTEM_ALERT_WINDOW` exemption is not used; Detach does not request that permission. Boot/update never launch this monitor. The `shortService` three-minute lifetime is inappropriate for a configurable pause up to an hour.

Android 12+ inexact alarms can be delivered late; Doze, OEM power management and process restrictions can add delay. Detach requests no new exact-alarm exemption: it uses exact delivery only where the platform already permits it, otherwise an inexact alarm. If delivery falls outside the original automatic-authority window, reconnect is refused and manual fallback remains. Restoring the reminder after a reboot does not restore authority to re-enable accessibility.
